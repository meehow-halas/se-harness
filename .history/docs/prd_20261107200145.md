# Project name: dev-harness
# Project description: This is a project intended to become a "harness layer" in the future. It will provide skills, agents, rules, and workflows for managing and developing software engineering projects

# How it will run:
It will be installed with npm, either from npm registry or github repository with npm install. After that it will be available in the system by accessing command 'dhs'

# Feature management
1. files - specs, prompts and logs are stored in files
   docs/features/
   docs/prompts
   docs/features-log
2. Jira - specs, prompts and logs handled with Jira MCP

Tracking features with files is the default, jira is optional.

# dhs commands
1. install/uninstall - indempotent, installs/uninstalls dhs on the machine

# Agents
| Agent | Model | Objective/Responsibilities |
|-------|-------|----------------------------|
| Architect | opus | Creates specs and prompts for feature. Is not creating literal instruction for Implementer what and where to do. Implementer is creating a plan of implementation for himself |
|Implementer | Sonnet | Implements feature using spec and prompt created by Architect. Divides implementation into smaller phases. Each phase, after it has finished, is consulted with Consultant to check the code quality |
| Consultant | haiku | Provides feedback for Implementer |
| Reviewer | sonnet | After the feature implementation is ready checks it for compliance with the specification. It does not evaluate code quality |

# Skills
| Skill | Description |
|-------|-------------|
| /dhs-init | indempotent, asks user about information to configure project to be able to use dhs in it |
| /dhs-planit | starts flow of creating specs for new features together with Architect |
| /dhs-doit | starts flow of implementing features together with Implementer |
| /dhs-checkit | starts flow of reviewing feature implementation together with Reviewer |
| /dhs-brainstorm | In general handles functionalities available with a group of personas to brainstorm an idea |
| /dhs-feature | Flow that includes /dhs-planit, /dhs-doit and /dhs-checkit |

# Agents is general
All agents can work in 3 modes. No mode is triggered by some command. All should be recognized by intent.
In general agents cannot make operations on git. There are exceptions described later. Feature status in Agents in details describe what status feature should have when specific agent is working with it.

## Agents modes
1. default - you have questions for me? ask! But one question at a time, not a list at the end.
2. semi-standalone - try to resolve problems as much as possible. Ask only with edge or critical cases.
3. standalone - don't asm me anything. All decision making is up to the agent.

Those modes work when talking with specific agent but also when running /dhs-feature. Each agent in chain knows what is the mode it is running in.

# Agents in details
## Architect
Architect should gather information about the feature and write specs. It can write spec from scratch just from user simple description but it can also be ordered to take what user already prepared in the files or jira and create on this basis. Created specification: abstract, requirements, Acceptance criteria, Architectural decisions. It can also recognize connections between features and mark them, both in files and in jira. It is crucial that architect is not creating bloated specs. If needed it divides and created smaller tasks to realize specified feature.
Feature status: backlog

## Implementer
Implements feature based on what Architect prepared. He plans his work by dividing if into smaller phases. Each phase, after it is finished, is checked by Consultant to check code quality. If there are any comments phase goes back to Implementer to fix it. This loop canno go for ever. Solution must be done in a smart way so loop Implementer<->COnsultant cannot go for infinity.
Before starting implementation this agent creates and switch to feature branch.
Feature status (when started): inProgress
Feature status (when completed): reviewReady

## Reviewer
It is checking the finished implementation agains the Architect specification. It checks the specs requirements, not the code quality. This is the only agent that can execute git commands.

After review is

Feature status (when started): inReview
Feature status (when completed): reviewDone
Feature status (when PR is done): done
